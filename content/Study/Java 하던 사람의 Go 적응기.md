## 요약

 > [!SUMMARY]
 > [[폐쇄망 전용 싱글 바이너리 워크플로우 도구 Deck 만들기|Deck]]을 Go로 시작하면서, Java를 먼저 익힌 입장에서 Go가 어떻게 다른지 빨리 파악하려고 정리한 노트다. 새 언어는 문법을 처음부터 외우기보다 "Java의 이 개념이 Go에서는 어디로 갔나"를 맞추면 습득이 빠르다. 문법 간결성, JVM 없는 단일 바이너리, 값과 포인터(모든 것이 참조는 아님), 암묵 인터페이스와 늦게 온 제네릭, slice와 map 그리고 없는 것들(Stream, Set), `for` 하나로 끝나는 반복, 예외 대신 에러값, 주석과 태그로 끝나는 문서와 스키마, goroutine 병렬 처리, 배터리 포함 툴체인 순서로 대응 관계를 맞춰 보았다.

 클래스는 struct+인터페이스로, 예외는 에러값으로, 스레드풀은 goroutine으로, JAR은 단일 바이너리로. 대응표를 만드니 며칠 만에 코드가 읽혔다.

## 1. 간결성: 외울 게 적다

Go를 처음 열고 제일 먼저 느낀 건 "작다"였다. 키워드가 25개뿐이고 문법이 한 가지 방식으로 수렴한다.

- <b>포맷이 하나다.</b> `gofmt`가 들여쓰기·정렬을 강제해서, Java의 코드 스타일 논쟁(중괄호 위치, 탭 대 스페이스)이 아예 없다. 포맷은 도구가 정하고 사람은 안 다툰다.
- <b>공개/비공개가 대소문자다.</b> `public`/`private` 키워드가 없다. 식별자가 대문자로 시작하면 공개, 소문자면 패키지 내부용이다. 접근제어자를 붙일 자리가 통째로 사라진다.
- 타입 추론(`x := 3`)이 있어 지역 변수는 타입을 거의 안 적는다.

Java에서 접근제어자·애노테이션·장황한 선언으로 표현하던 것들이 규칙 한 줄로 대체되거나 사라진다. 처음엔 "이걸로 되나" 싶다가, 외울 게 적어 금세 코드를 읽게 됐다.

## 2. JVM이 없다: 단일 정적 바이너리

Java 하던 사람에게 제일 실감 나는 차이다. Go는 `go build` 한 번이면 <b>런타임이 필요 없는 단일 실행 파일</b>이 나온다. JVM도, JRE 설치도, classpath도, JAR 묶음도 없다.

- <b>배포가 파일 하나.</b> 대상 서버에 Java를 설치할 필요가 없다. 바이너리만 두면 그대로 동작한다. Deck을 Go로 정한 이유도 여기에 있다. 폐쇄망에 JVM을 반입하고 유지하는 부담 없이 바이너리 하나만 넣으면 되기 때문이다.
- <b>크로스컴파일이 공짜다.</b> `GOOS`/`GOARCH`만 바꾸면 리눅스에서 macOS·ARM 바이너리를 뽑는다. Java의 "한 번 빌드해 어디서나(JVM 위에서)"와 달리, Go는 플랫폼별 네이티브 바이너리를 아예 미리 다 만들어둔다.
- <b>의존성은 `go.mod` 하나.</b> Maven/Gradle 같은 별도 빌드 도구가 아니라 `go` 명령에 내장돼 있고, 컴파일이 빠르다.

"빌드란 JAR과 JVM을 만드는 것"이라고 머릿속에 굳어져 있었는데, "빌드란 그 자체로 실행되는 파일을 만드는 것"으로 관점을 바꾸는 것이 첫 관문이었다.

## 3. 값과 포인터: struct가 값이다

Java에서는 객체는 모두 참조였고 원시 타입만 값이었다. 반면 Go는 struct가 기본적으로 값이라서 대입하거나 함수에 넘기면 복사된다. 따라서 원본을 고치려면 포인터(`*T`, `&x`)를 명시해야 한다.

```go
func rename(u User)  { u.Name = "x" }   // 복사본만 바뀜 (원본 그대로)
func rename(u *User) { u.Name = "x" }   // 포인터로 넘겨야 원본이 바뀜
```

메서드도 값 리시버(`func (u User)`)와 포인터 리시버(`func (u *User)`)로 갈린다. Java에선 신경 쓸 일 없던 "이건 복사되나 공유되나"를 매번 의식하게 되는데, 익으면 오히려 변경 범위가 코드에 드러나 좋다.

여기에 nil과 zero value 개념이 더해진다. Go에는 모든 타입에 쓸 수 있는 영값(zero value)이 있다. 숫자 `0`, 문자열 `""`, 불리언 `false`, 포인터와 slice와 map은 `nil`이다. 선언만 해도 쓸 만한 초기값이므로 Java에서 흔하던 `null` 초기화 실수와 NPE 문제 가능성이 줄어든다. `Optional`도 존재하지 않으며 "있을 수도 없을 수도" 있는 값은 `value, ok := m[key]`나 다중 반환으로 표현한다.

## 4. 타입 시스템: 암묵 인터페이스, 늦은 제네릭

- <b>클래스도 상속도 없다.</b> `class`/`extends` 대신 `struct`에 메서드를 붙이고, 재사용은 상속이 아니라 <b>조합(embedding)</b>으로 한다.
- <b>인터페이스는 암묵적으로 만족</b>한다. Java처럼 `implements`를 선언하지 않는다. 메서드 시그니처만 맞으면 그 인터페이스가 된다. 그래서 Go는 "작은 인터페이스를 받고 struct를 반환하라"는 관용이 강하다. 소비하는 쪽에서 필요한 만큼만 인터페이스를 정의한다.
- <b>제네릭은 늦게(1.18) 왔다.</b> 오래 없다가 타입 파라미터가 들어왔다. Java 제네릭(타입 소거)에 익숙하면 문법만 다를 뿐 개념은 비슷하지만, Go 코드는 여전히 인터페이스와 구체 타입으로 푸는 경우가 더 많다.

## 5. 자료구조: slice·map, 그리고 없는 것들

Java의 풍부한 컬렉션(`List`/`Map`/`Set`/`Queue`)과 스트림에 익숙하면, Go의 단출함이 처음엔 허전하다.

- 언어 내장은 배열, <b>slice</b>(가변 길이 배열), <b>map</b>이 사실상 전부다. `ArrayList`↔slice, `HashMap`↔map로 대응된다.
- <b>Set이 없다.</b> `map[T]struct{}`(값 없는 맵)로 흉내 낸다.
- <b>Stream API가 없다.</b> `filter/map/collect` 대신 그냥 `for`를 쓴다. 처음엔 답답한데, 데이터 흐름이 눈에 보여 디버깅은 편하다. 정렬 등은 표준 `sort`/`slices` 패키지로 한다.

컬렉션 프레임워크의 다양한 자료구조를 골라 쓰던 습관을, "slice와 map으로 웬만한 건 다 한다"로 바꾸는 과정이었다.

## 6. 반복문은 for 하나

Java는 반복만 놓고 보아도 `for`, `while`, `do-while`, 향상된 for, `Iterator`, 스트림까지 갈래가 많다. 반면 Go는 반복 키워드가 `for` 하나다.

```go
for i := 0; i < n; i++ { }      // 전통적 for
for cond { }                     // while 대용
for { }                          // 무한 루프
for i, v := range items { }      // for-each 대용 (인덱스, 값)
```

`range`가 Java의 향상된 for와 `Iterator`를 겸해서 slice, map, 채널, 문자열을 모두 순회한다. 커스텀 순회도 최신 Go(1.23 이상)는 함수를 넘겨 `range`로 도는 이터레이터를 지원한다. 반복의 표현 수단이 하나로 좁혀지므로 "이 경우엔 while이 나은가" 같은 선택 자체가 존재하지 않는다.

## 7. 예외 대신 에러를 값으로

가장 크게 부딪히는 지점이다. Go에는 checked exception도 `try/catch`도 존재하지 않는다. 실패는 예외를 던지는 방식이 아니라 반환값으로 돌려준다. 함수가 결과와 에러를 함께 반환하고(`(T, error)`), 호출부가 매번 확인한다.

```go
f, err := os.Open(path)
if err != nil {
    return fmt.Errorf("open config: %w", err)   // 컨텍스트를 덧대 다시 반환
}
```

- Java는 예외가 콜스택을 자동으로 타고 올라간다. 반면 Go는 각 단계에서 직접 에러를 올려보낸다. 다소 장황하지만 에러가 어디서 발생하고 어디로 흐르는지가 코드에 그대로 드러난다.
- 예외 계층(`catch (IOException e)`) 대신 `errors.Is`(특정 센티넬 에러인지 판별)와 `errors.As`(특정 타입인지 판별)로 분기한다.
- `%w`로 감싸면 원인 체인이 유지되므로 Java의 `caused by`에 해당하는 맥락을 얻는다.
- `panic`은 `RuntimeException`처럼 보이지만 용도가 다르다. 정상적인 실패에는 쓰지 않고 "일어나면 안 되는 상태"에만 사용한다.

Deck에서도 정상 실패는 전부 에러 반환으로 처리하고, 메시지는 `"open config: %w"`처럼 짧게 유지하며, 프로세스 종료(`os.Exit`)는 `main`에서만 수행하고 나머지는 `run`류 함수가 에러를 돌려주도록 두었다. 처음에는 `if err != nil`이 번거로웠지만 익으니 "이 함수가 무엇을 실패할 수 있는지"가 시그니처에 드러나서 오히려 편했다.

## 8. 문서와 스키마: 주석과 태그로 끝난다

Java에서는 문서는 Javadoc으로, 직렬화 스키마는 애노테이션(`@JsonProperty` 등)으로 표현했다. 반면 Go는 둘 다 더 가볍다.

- <b>문서 = 주석 그 자체.</b> 공개 식별자 위 주석이 곧 문서다. `@param` 같은 태그 없이 평문으로 쓰면 `go doc`과 pkg.go.dev가 그대로 렌더한다.
- <b>스키마 = struct 태그.</b> 필드 뒤 백틱 태그로 직렬화 규칙을 선언한다. Jackson 애노테이션에 대응하지만 한 줄이다.

```go
type Config struct {
    Root    string `json:"root" yaml:"root"`
    DryRun  bool   `json:"dry_run" yaml:"dry_run"`
}
```

이 struct 하나가 JSON과 YAML (역)직렬화 스키마이며, 주석을 달면 그대로 문서가 된다. Deck은 여기서 더 나아가 [[Cobra로 Go CLI 만들기|Cobra]] 명령 정의에서 CLI 레퍼런스 문서를 통째로 생성한다. "코드가 곧 스키마이자 문서"라는 감각이 애노테이션과 Javadoc 조합보다 손이 덜 갔다.

## 9. 병렬처리: goroutine과 채널

Java의 동시성은 `Thread`, `ExecutorService`, `Future`/`CompletableFuture`, `synchronized`로 층이 두껍다. 반면 Go는 이것을 goroutine과 채널이라는 두 원시로 좁힌다.

```go
ch := make(chan int)
go worker(ch)          // goroutine 시작: 함수 앞에 go 만 붙인다
result := <-ch         // 채널로 결과를 받는다 (동기화가 채널에 내장)
```

- goroutine은 OS 스레드가 아니라 런타임이 스케줄링하는 경량 실행 단위다. 스택이 작아(수 KB) 수천 개를 띄워도 부담이 적다. Java 스레드를 풀로 아껴 쓰던 것과 대조된다. (Java도 21의 가상 스레드로 이 지점에 가까워졌다.)
- 공유 상태에 락을 거는 대신 <b>"메모리를 공유해 통신하지 말고, 통신으로 메모리를 공유하라"</b>가 기본 철학이다. 값을 채널로 주고받으면 그 자체가 동기화이므로 `synchronized`가 필요한 상황이 줄어든다.
- 여러 채널을 기다릴 때는 `select`를 쓰고, 취소와 타임아웃은 `context`로 흘려보낸다. 상태 공유가 더 나을 때는 `sync.Mutex`/`WaitGroup`도 활용할 수 있다.

가볍다고 아무 데나 만들면 안 된다. Deck에서는 소유자와 종료 경로가 없는 goroutine을 프로덕션 코드에 만들지 않기로 하고, 채널 버퍼는 기본 0(또는 1)으로 두기로 정했다. 가벼운 만큼 규칙으로 경계를 세워 둔 셈이다.

## 10. 툴체인과 테스트: 배터리 포함

Java에서는 빌드(Maven/Gradle), 테스트(JUnit), 목(Mockito), 포맷터가 모두 별도 생태계였다. 반면 Go는 이것을 표준 툴체인에 넣어 두었다.

- `go fmt`(포맷), `go vet`(정적 분석), `go test`(테스트), `go doc`(문서)이 전부 기본 명령이다.
- 테스트는 표준 `testing` 패키지 하나로 충분하며, <b>테이블 주도 테스트</b>(입력과 기대값 표를 도는 방식)가 관용이다. 별도 프레임워크가 거의 필요하지 않다.
- <b>레이스 디텍터</b>(`go test -race`)가 내장되어 있다. 이 도구는 동시성 버그를 실행 중에 잡아 주므로 goroutine을 안심하고 쓰게 해 준다.
- 프로파일러(pprof)도 표준이다.

"도구를 고르고 붙이는" 단계가 거의 없어서 언어를 배우는 것과 생태계를 세팅하는 것이 분리되어 있지 않았다. 이것도 습득 속도를 높여 준 요소였다.

## 11. 그리운 것
 
Java에서 그리운 것도 있다. Spring 같은 성숙한 프레임워크 생태계와 예외가 스택트레이스를 자동으로 남겨 주던 편함이 대표적이다. 반대로 Go는 문법이 작고 방식이 하나로 수렴하므로 팀이 커져도 남이 쓴 코드가 내 것과 비슷하게 읽힌다. 새 문법을 백지에서 외우기보다 아는 Java 개념이 Go에서 어디에 대응되는지부터 맞추면 된다.
