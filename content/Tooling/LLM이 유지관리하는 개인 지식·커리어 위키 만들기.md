## 요약

> [!SUMMARY]
> 작업하면서 남긴 노트·장애 기록·리포 히스토리를 커리어 자산으로 축적하려고, LLM(Claude Code)이 직접 작성·유지관리하는 개인 위키를 만들었다. 손대지 않는 원본(`raw/`)과 LLM이 소유하는 위키(`wiki/`)를 나누고, 소스 종류별 프론트매터 스키마와 운영 규칙을 `CLAUDE.md` 한 곳에 명시했다. 검색은 BM25+벡터+리랭킹 하이브리드(qmd)를 MCP로 연결했고, 다른 프로젝트 세션에서도 이 위키를 조회할 수 있도록 Claude Code 플러그인으로 패키징했다.

나는 기억력이 나쁜 편이다. 작업하면서 노트는 열심히 남기는데, 정작 반년 뒤 "그때 그 etcd 문제 어떻게 풀었더라"를 다시 찾을 때는 어디에 적었는지부터 찾아야 한다. 이력서를 쓸 때도 마찬가지다. 분명히 한 일은 많은데 구체적인 근거가 여러 곳에 흩어져 있어서, 매번 처음부터 다시 발굴해야 했다.

그래서 흩어진 기록을 한 곳에 쌓아 두는 개인 위키를 만들기로 했다. 다만 내가 손으로 관리하는 위키는 번거로움 때문에 지금까지 모두 실패했으므로, 이번에는 LLM에게 관리를 맡기는 방향을 택했다.

## 1. RAG 대신 위키

처음에는 노트를 폴더에 모아 넣고 RAG로 검색하면 충분하다고 생각했다. 실제로 대부분의 사용자가 그렇게 활용한다. 파일을 많이 넣고 질문하면 관련 청크를 찾아 답을 만든다. 이 방식의 약점은 <b>축적이 없다</b>는 점이다. LLM이 매 질문마다 지식을 처음부터 다시 발견한다. 다섯 개 문서를 종합해야 답이 나오는 질문이라면, 매번 해당 문서들의 조각을 새로 찾아서 결합해야 한다. 축적되는 지식이 없다.

내가 원했던 방향은 정반대였다. 소스를 추가할 때마다 LLM이 그것을 읽고 핵심을 추려서 <b>기존 위키에 통합</b>하는 구조였다. 엔티티 페이지를 갱신하고, 개념 요약을 고치고, 새 소스가 기존 주장과 모순되면 그 모순을 표시해 두는 작업이다. 한 번 편찬된 지식을 최신 상태로 유지하고, 질문할 때는 이미 정리된 위키를 읽는 구조다. 상호 참조도, 모순 표시도, 종합 정리도 질문 시점이 아니라 수집 시점에 이미 완료되어 있다.

사람이 위키를 포기하는 이유는 읽기나 사고가 힘들어서가 아니다. 상호 참조를 업데이트하고, 요약을 최신화하고, 수십 개 페이지의 일관성을 맞추는 <b>기록 관리(bookkeeping)</b>가 번거롭기 때문이다. LLM은 이런 작업을 부담스러워하지 않고 한 번에 열댓 개 파일을 수정한다. 유지관리 비용이 거의 0에 가까워지므로 위키가 유지된다. 이 아이디어 자체는 내가 낸 것이 아니라 "LLM이 유지관리하는 위키"라는 패턴 글에서 가져왔고, 내 도메인(DevOps·커리어)에 맞게 구체화하는 것을 목표로 삼았다.

## 2. raw와 wiki, 그리고 스키마

구조는 세 층으로 나눴다.

- <b>`raw/`</b>: 내가 큐레이션한 원본이다. LLM은 읽기만 하고 절대 수정하지 않는다. 단일 진실 공급원(source of truth)이다.
- <b>`wiki/`</b>: LLM이 생성·관리하는 마크다운이다. 페이지 생성, 갱신, 상호 참조 유지, 일관성 관리가 모두 LLM의 담당 영역이다. 나는 읽고, LLM은 쓴다.
- <b>스키마(`CLAUDE.md`)</b>: 위키의 구조·규칙·워크플로우를 LLM에게 알려주는 문서이다. 이 문서가 가장 중요한 파일이다. 이 문서 하나만으로 LLM이 범용 챗봇이 아니라 규율 있는 위키 관리자가 된다.

`raw/`는 성격별로 더 세분화했다. 내가 직접 쓴 문서(`my-docs/`), 외부 스크랩(`clippings/`), 지식 대화 세션 노트(`conversations/`), 이미지 같은 첨부(`assets/`)로 나눴다. GitHub 리포는 조금 다르게 다룬다. 코드를 raw에 복사해 두면 금방 낡으므로, `repos.md`에 주소만 등록해 두고 수집할 때는 `gh` CLI나 GitHub MCP로 원격 조회한다. 커밋 히스토리와 PR을 살펴보면 "내가 실제로 무슨 일을 했는지"가 드러나는데, 이 기록이 커리어 근거로 꽤 쓸모가 있다.

> [!NOTE]
> `raw/`를 불변으로 유지하도록 고정한 점이 이 구조의 핵심이다. LLM이 원본을 수정하기 시작하면 진실 공급원의 신뢰성이 무너지고, 위키의 어떤 주장이 어느 원본에서 나왔는지에 대한 추적이 깨진다. 그래서 스키마 금지 사항 맨 위에 "raw는 절대 수정하지 않는다"를 명시했다. 예외는 진행 중인 대화 세션이 자기 파일을 append-only로 쓰는 경우뿐이다.

`wiki/` 아래는 목적별 카테고리로 나눴다. 소스 1:1 요약(`sources/`), 경력 관리(`career/`), 트러블슈팅 케이스(`troubleshooting/`), 개념 백과(`concepts/`), 도구·서비스 엔티티(`entities/`), 프로젝트 작업 기록(`work-log/`)이다. 하나의 소스가 여러 카테고리에 동시에 기여한다. 예를 들어 K8s 마이그레이션 회고 문서 하나를 수집하면, 소스 요약 + 커리어 성과 + etcd 트러블슈팅 케이스 + 마이그레이션 개념 + 작업 기록에 모두 기록이 남는다.

## 3. 소스별 프론트매터 스키마

카테고리마다 프론트매터 스키마를 정해 두었다. LLM이 페이지를 만들 때 이 형식을 따르도록 하고, 나중에 Obsidian Dataview로 "가장 많이 등장한 개념 TOP 20" 같은 뷰를 뽑을 여지를 남겼다. 트러블슈팅 페이지는 다음과 같이 잡았다.

```yaml
# wiki/troubleshooting/ 페이지의 프론트매터.
# 필수 섹션(상황/원인/해결/교훈)까지 스키마에 규정해 케이스 형식을 통일한다.
---
title: "제목"
type: troubleshooting
date_occurred: YYYY-MM-DD
date_resolved: YYYY-MM-DD
severity: critical | major | minor
tags: []
related: []
---
```

개념·엔티티 페이지에는 `source_count` 필드를 두었다. 해당 개념이 몇 개의 소스에서 언급됐는지 세는 값인데, 이 값이 쌓이면 "내가 실제로 자주 다룬 기술"이 자연스럽게 드러난다. 커리어 페이지는 `period`·`role`·`company`를, 작업 기록은 `date_start`·`date_end`·`project`를 갖는 식으로 목적에 맞게 필드를 달리했다.

`related`는 Obsidian이 링크로 인식하도록 형식을 다소 까다롭게 정했다. 한 줄로 늘어놓으면 링크로 인식되지 않으므로, 반드시 여러 줄 YAML 배열에 따옴표로 감싼 위키링크를 쓰도록 했다.

```yaml
# 이렇게 써야 Obsidian이 related를 실제 링크로 인식한다.
related:
  - "[[page-a]]"
  - "[[page-b]]"
```

파일명은 영어 `kebab-case`를 사용하고, 제목(H1)은 한국어를 사용했다. 한글 파일명은 Obsidian URL 인코딩이나 git 호환성에서 성가신 문제를 일으키기 때문이다. 태그는 한영 병기(`[쿠버네티스, kubernetes]`)를 권장했는데, 한국어가 교착어라 형태소 분석 없이는 검색이 잘 되지 않는 문제를 나중에 우회하기 위한 대비책이었다.

## 4. 대화와 클리핑의 역할 분리

만들다 보니 소스 하나가 애매해졌다. 내가 LLM과 나눈 대화 자체를 소스로 남기고 싶은데, 그 안에는 성격이 다른 두 정보가 섞여 있었다. 하나는 "내 의도·상황·판단"(내 환경에서는 이렇게 쓴다, 이래서 이것을 골랐다)이고, 다른 하나는 "개념 자체의 객관 사실"(X가 무엇인가, 어떻게 동작하는가)이다. 이 둘은 <b>검증 주체가 다르다</b>. 앞선 정보는 내가 말한 순간 자명하지만, 뒤선 정보는 공식 문서 같은 출처로 검증해야 한다.

그래서 raw를 둘로 갈랐다.

- <b>`raw/conversations/`</b>: 내 의도·상황·개념 간 관계다. 검증 주체는 나다.
- <b>`raw/clippings/`</b>: 키워드·개념 자체의 객관 정보다. 검증 주체는 출처이다.

개념 자체에 대한 사실은 conversations에 넣지 않는다. 내가 대화 중에 "TCP 핸드셰이크가 뭐였지"라고 물으면, LLM은 그것을 대화 노트에 적는 것이 아니라 공식 문서를 fetch해서 클리핑으로 처리한다. 위키 페이지는 결국 이 둘의 합성이다: "정의·동작(클리핑 기반)" + "내 환경 맥락(대화 기반)".

여기에 규칙을 몇 개 더 걸었다. 클리핑은 <b>고아 금지</b>다. 어떤 주장을 뒷받침하려고 인용했는지(`supporting_claims`)가 최소 하나는 있어야 저장한다. 탐색하다 그냥 열어본 자료는 저장하지 않고 폐기한다. 그리고 클리핑의 `## 원문` 섹션은 fetch 결과를 그대로 보존한다. paraphrase·요약·불릿 변환을 모두 금지했다. LLM이 "원문에 따르면 ~다"로 재서술하는 순간 인용의 신뢰도가 깨지기 때문이다.

대화 세션에는 가드레일도 하나 뒀다. 대화 중에는 `wiki/`를 절대 건드리지 못하게 막았다.

> [!IMPORTANT]
> 대화하면서 동시에 위키까지 수정하면, 아직 검증되지 않은 즉흥적 판단이 곧바로 위키에 반영된다. 그래서 대화 세션은 `raw/conversations/`와 `raw/clippings/`만 쓸 수 있고, 위키 반영은 반드시 별도 세션의 ingest 단계에서 수행한다. 세션 중에 위키 변경 명령을 호출하면 거절하도록 커맨드에 규정했다. 대화의 개방성과 위키의 확정성을 분리한 것이다.

## 5. 하이브리드 검색 MCP

위키가 작을 때는 `index.md` 하나로 충분하다. 카테고리별 페이지 목록에 한 줄 요약이 달려 있어서, 질의가 들어오면 LLM이 인덱스부터 읽고 관련 페이지로 들어간다. 실제로 페이지 수백 개 규모까지는 임베딩 인프라 없이도 이 방식이 놀랍도록 잘 작동한다.

지금은 개념 40여 개, 엔티티 35개, 트러블슈팅 케이스 36개, 소스 요약 30여 개까지 쌓였다. 이 규모부터는 인덱스만으로 탐색이 점점 어려워져서 제대로 된 검색을 붙였다. [qmd](https://github.com/tobi/qmd)를 골랐는데, 마크다운용 로컬 검색 엔진이라 온디바이스로 <b>BM25 + 벡터 검색 + LLM 리랭킹</b>을 모두 수행한다. 클라우드로 내 노트가 나갈 일이 없다는 점이 마음에 들었다.

qmd는 CLI와 MCP 서버라는 두 인터페이스를 제공한다. LLM이 셸로 검색 스크립트를 호출하는 것보다, MCP로 노출해서 네이티브 도구처럼 호출하는 쪽이 응답도 빠르고 에러 처리도 깔끔하다. Claude Code라면 프로젝트 루트 `.mcp.json`에 등록하면 설정이 끝난다.

```json
// .mcp.json — qmd를 MCP 서버로 붙인다. 이러면 LLM이 wiki 검색을 네이티브 도구로 호출한다.
{
  "mcpServers": {
    "qmd": { "command": "qmd", "args": ["mcp"] }
  }
}
```

위키를 수정하면 인덱스가 낡아지므로 갱신이 필요하다. 페이지를 추가·수정한 뒤 인덱스와 임베딩을 다시 만든다.

```bash
# 위키 페이지 변경 후 검색 인덱스와 벡터 임베딩을 재생성한다.
qmd update && qmd embed
```

> [!INFO]- 한국어 검색 잡담
> 한국어는 교착어라 형태소 분석 없이는 검색이 잘 안 걸린다. "쿠버네티스를"과 "쿠버네티스가"가 다른 토큰으로 잡히는 식이다. qmd의 한국어 토크나이징이 완벽하진 않아서, 프론트매터 태그에 영어를 병기하고 `index.md`에도 영어 키워드를 섞어두는 걸로 어느 정도 우회했다. 완전한 해결은 아니고, 그냥 실용적으로 타협한 지점이다.

## 6. 다른 세션에서 조회하는 플러그인

위키를 한참 쓰다 보니 문제가 하나 생겼다. 정작 이 지식이 필요한 순간은 <b>다른 프로젝트를 작업할 때</b>인데, 그때는 위키 저장소가 아니라 남의 코드베이스에서 세션을 열고 있다는 것이다. 위키를 조회하려고 매번 디렉토리를 옮기는 건 번거로웠다.

그래서 조회 기능만 분리해서 Claude Code 플러그인으로 패키징했다. 이 플러그인은 위키를 <b>읽기 전용으로 조회</b>만 한다. 수집·수정은 원래 저장소에서 수행하고, 다른 세션에서는 검색만 하는 운영 모델이다. skill을 네 개 넣었다.

- `wiki-query`: 자유 질의
- `career-history`: 경력 히스토리 조회
- `task-trace`: 개별 작업·장애·프로젝트 추적
- `career-evidence`: 특정 기술의 경력 근거 수집(이력서·면접 준비용)

플러그인이라는 특성상 위키 저장소 경로를 하드코딩할 수 없다는 점이 문제였다. 그래서 실행 시점에 환경을 확인하는 작은 런타임 헬퍼를 두었다. 환경변수(`OBSIDIAN_WIKI_ROOT`)가 있으면 그것을 사용하고, 없으면 현재 경로에서 상위로 올라가며 `wiki/index.md`가 있는 저장소를 찾는다. qmd CLI가 설치되어 있는지도 여기서 확인한다.

조회 전략은 세 단계 폴백으로 잡았다.

1. <b>qmd MCP 우선</b>: 탐색과 카테고리 횡단 검색
2. <b>qmd CLI</b>: MCP가 없지만 qmd는 설치되어 있을 때
3. <b>로컬 Glob/Grep/Read</b>: 위키 루트를 찾을 수 있으면 결정적 읽기와 근거 검증

즉 탐색은 qmd로 넓게 수행하고, 정밀 검증은 로컬 파일 읽기로 좁힌다. 단순 검색 래퍼가 아니라 위키 구조 이해와 근거 검증을 결합한 조회 계층에 가깝다. 각 skill의 답변은 마지막에 `[[위키링크]]`로 근거 페이지를 명시하도록 했고, 위키에 없는 경험은 지어내지 않도록 제약을 걸었다. 이력서 근거를 뽑을 때 없는 것을 그럴듯하게 과장하면 그것이 가장 위험하기 때문이다.

## 7. 운영 흐름과 규칙

일상 운영은 세 동작으로 돈다.

- <b>수집(Ingest)</b>: 새 소스를 읽고, 어느 카테고리에 어떤 페이지를 만들지·고칠지 나에게 먼저 제안한다. 확인하면 소스 요약 → 관련 페이지 갱신 → `index.md` 갱신 → `log.md` 기록 순으로 처리한다. 나는 소스를 하나씩 넣으면서 요약을 읽고 방향을 잡는 방식을 선호한다.
- <b>질의(Query)</b>: `index.md`로 1차 탐색하고, 상세가 필요하면 qmd로 탐색 범위를 넓힌 뒤 관련 페이지를 읽어 종합한다. 답변이 저장할 가치가 있으면(비교, 새 연결, 종합 정리) 새 페이지로 저장을 제안한다. 내 탐색 활동도 위키에 계속 누적되는 것이다.
- <b>점검(Lint)</b>: 주기적으로 위키의 건강 상태를 확인한다. 깨진 링크, 미등록 페이지, 인바운드 링크 없는 고아 페이지, 페이지 간 모순, 언급만 되고 페이지가 없는 개념 같은 항목을 점검한다.

두 개의 특수 파일이 이 흐름을 지탱한다. `index.md`는 콘텐츠 중심 카탈로그이고, `log.md`는 시간순 활동 기록(append-only)이다. 로그 항목을 일관된 접두사로 시작하도록 해 두면(`## [2026-07-21] ingest | 제목`) 유닉스 도구로 파싱할 수 있다. 최근 활동 다섯 개는 다음과 같이 확인한다.

```bash
# log.md에서 최근 활동 항목 5개만 뽑아본다.
grep "^## \[" log.md | tail -5
```

새 세션이 열리면 LLM이 `CLAUDE.md` → `index.md` → `log.md` 최근 항목을 먼저 읽도록 규정했다. 이것이 사실상 위키가 해결하는 가장 실전적인 문제다. LLM 에이전트는 세션이 끝나면 대화를 잊는다. 어제 두 시간 동안 깊게 진행한 분석도 새 세션에서는 처음부터 다시 시작한다. 위키가 있으면 어제의 분석이 페이지로 남아 있고, 오늘은 인덱스만 읽고 거기서 이어간다. 커밋도 수집 단위로 끊어서(`ingest: 소스 제목`) 소스 하나가 위키에 어떤 변화를 주었는지 diff로 바로 확인할 수 있게 했다.

아직 다듬을 부분이 많다. 한국어 검색은 여전히 미흡하고, 스키마도 소스가 쌓일 때마다 조금씩 수정하는 중이다. 처음부터 완벽하게 세우려는 것이 아니라, LLM과 함께 몇 번 운영하면서 내 도메인에 맞게 다듬어 가는 중이다.
