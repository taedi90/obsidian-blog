> [!SUMMARY]
> 쿠버네티스 서비스(Service)는 레이블 셀렉터(Label Selector)를 이용해 특정 레이블을 가진 파드(Pod)들을 찾아내고, 이 파드들의 IP 목록을 엔드포인트(Endpoints) 오브젝트로 관리한다. 사용자가 서비스에 요청을 보내면, 각 노드의 kube-proxy가 이 엔드포인트 목록을 기반으로 실제 파드에게 트래픽을 전달하고 로드 밸런싱을 수행한다.

## 1. 개요

쿠버네티스에서 파드(Pod)는 언제든지 사라지고 새로 생성될 수 있는 비영구적인 존재다. 파드가 재시작되면 IP 주소 또한 바뀌기 때문에, 특정 파드를 직접 참조하여 통신하는 것은 매우 불안정한 방식이다. 이러한 문제를 해결하기 위해 쿠버네티스는 <b>서비스(Service)</b>라는 추상화 계층을 제공한다.

서비스는 여러 파드를 하나의 논리적인 그룹으로 묶고, 이 그룹에 접근할 수 있는 고유하고 안정적인 네트워크 엔드포인트(Endpoint)를 부여하는 역할을 한다. 덕분에 클라이언트는 파드의 생명주기나 IP 변경에 신경 쓸 필요 없이, 일관된 주소로 애플리케이션에 접근할 수 있게 된다.

## 2. 서비스와 파드의 연결 원리

서비스가 어떻게 자신과 연결될 파드를 찾아내는지를 이해하는 것이 핵심이다. 그 중심에는 <b>레이블 셀렉터(Label Selector)</b>가 있다.

### 2-1. 레이블 셀렉터(Label Selector) 기반 매칭

서비스는 `selector` 필드에 정의된 레이블(Label)을 기준으로, 동일한 레이블을 가진 파드들을 자신의 백엔드로 삼는다.

아래는 `app: web`과 `tier: frontend`라는 두 개의 레이블을 가진 파드를 찾는 서비스의 정의 예시다.

```yaml
# 'app: web', 'tier: frontend' 레이블을 가진 파드를 찾는 서비스
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  selector:
    app: web
    tier: frontend
  ports:
  - protocol: TCP
    port: 80       # 서비스가 노출할 포트
    targetPort: 8080 # 서비스가 트래픽을 전달할 파드의 컨테이너 포트
```

위 서비스와 연결되기 위해 파드는 `metadata.labels` 필드에 해당 레이블들을 모두 가지고 있어야 한다.

```yaml
# 위 서비스의 selector와 일치하는 레이블을 가진 파드
apiVersion: v1
kind: Pod
metadata:
  name: web-pod
  labels:
    app: web
    tier: frontend
spec:
  containers:
  - name: web-container
    image: nginx
    ports:
    - containerPort: 8080
```

### 2-2. 연결 과정 상세 분석

서비스와 파드가 연결되는 과정은 쿠버네티스 컨트롤러들에 의해 자동으로 처리된다.
1.  <b>서비스 생성</b>: 사용자가 `kubectl`을 통해 서비스 매니페스트를 API 서버에 제출한다.
2.  <b>엔드포인트 컨트롤러 동작</b>: API 서버는 이 정보를 `etcd`에 저장한다. 엔드포인트 컨트롤러(Endpoint Controller)는 새로운 서비스가 생성된 것을 감지하고, 서비스의 `selector`와 일치하는 레이블을 가진 파드를 클러스터 내에서 검색한다.
3.  <b>엔드포인트 오브젝트 생성</b>: 컨트롤러는 검색된 파드들의 IP 주소와 포트 정보를 모아 <b>엔드포인트(Endpoints)</b>라는 별도의 오브젝트를 생성하여 저장한다. 이 오브젝트는 서비스와 파드를 잇는 다리 역할을 한다.

아래는 `web-service`에 의해 자동으로 생성된 엔드포인트 오브젝트의 예시다.

```yaml
# web-service에 연결된 파드들의 IP와 포트 정보를 담고 있다.
apiVersion: v1
kind: Endpoints
metadata:
  name: web-service # 서비스와 동일한 이름으로 생성된다.
subsets:
- addresses:
  - ip: 10.244.1.5
  - ip: 10.244.2.3
  ports:
  - port: 8080
    protocol: TCP
```

4.  <b>지속적인 동기화</b>: 이후에도 컨트롤러는 파드의 생성, 삭제, 레이블 변경 등을 계속 감시하며 엔드포인트 오브젝트를 항상 최신 상태로 유지한다.

## 3. 트래픽 라우팅 과정과 kube-proxy

서비스의 IP(ClusterIP)는 가상의 IP다. 실제 트래픽 전달은 클러스터의 모든 노드에서 실행되는 <b>kube-proxy</b>라는 컴포넌트가 담당한다.

```mermaid
graph LR
    A[클라이언트 파드] --> B{web-service (가상 IP)};
    subgraph "Node"
        B --> C[kube-proxy];
        C -- iptables/IPVS 규칙 --> D[web-pod-1 (10.244.1.5)];
        C -- iptables/IPVS 규칙 --> E[web-pod-2 (10.244.2.3)];
    end
```

1.  클라이언트가 서비스의 ClusterIP로 요청을 보낸다.
2.  노드에 있는 `kube-proxy`가 이 요청을 가로챈다. `kube-proxy`는 엔드포인트 오브젝트를 통해 실제 파드들의 IP 주소 목록을 이미 알고 있다.
3.  `kube-proxy`는 이 목록을 바탕으로 `iptables` 규칙이나 `IPVS` 모드를 사용하여 요청을 백엔드 파드 중 하나로 전달(포워딩)한다. 이때 기본적인 로드 밸런싱(기본값: 라운드 로빈)이 수행된다.

> [!INFO]
> `kube-proxy`는 이름과 달리 실제 프록시 서버가 아니다. 트래픽을 직접 처리하는 것이 아니라, 커널의 넷필터(Netfilter) 기능을 이용해 패킷의 목적지 주소를 바꾸는 방식(DNAT)으로 동작하는 네트워크 컨트롤러에 가깝다고 볼 수 있다.

## 4. 서비스 타입별 특징

서비스는 노출 방식에 따라 몇 가지 타입을 가진다.
- <b>ClusterIP</b>: 기본값이며, 클러스터 내부에서만 접근 가능한 가상 IP를 할당한다. 클러스터 내부의 다른 파드들이 이 서비스를 호출할 때 사용된다.
- <b>NodePort</b>: ClusterIP의 모든 기능을 포함하며, 추가로 모든 노드의 특정 포트(기본 범위: 30000-32767)를 통해 외부에서 서비스에 접근할 수 있게 해준다. `<NodeIP>:<NodePort>`로 접속하면 서비스에 연결된다.
- <b>LoadBalancer</b>: NodePort의 모든 기능을 포함하며, AWS, GCP, Azure 등 클라우드 플랫폼의 외부 로드 밸런서를 프로비저닝하고 서비스에 연결한다. 외부 IP 주소를 가지게 되어 인터넷에서 직접 접근이 가능하다.
- <b>ExternalName</b>: 클러스터 외부의 서비스를 DNS CNAME 레코드로 매핑하여, 내부 서비스처럼 별칭으로 사용할 수 있게 해준다.

## 5. 연결 실패 시 디버깅

> [!NOTE]
> 실무에서 서비스 연결 문제를 마주쳤을 때, 대부분의 원인은 <b>레이블 불일치</b>였다. 서비스의 `selector`와 파드의 `labels`가 정확히 일치하는지 확인하는 것이 가장 빠른 해결책인 경우가 많았다.

서비스가 예상대로 동작하지 않을 때 아래 명령어들을 통해 원인을 파악할 수 있다.

```bash
# 1. 서비스의 selector와 할당된 IP 확인
kubectl describe svc web-service

# 2. 서비스에 연결된 파드 목록(엔드포인트) 확인
# 이 명령의 결과가 비어있다면, 레이블이 일치하는 파드가 없다는 뜻이다.
kubectl get endpoints web-service

# 3. 파드들의 레이블 직접 확인
kubectl get pods --show-labels
```

주요 점검 사항은 다음과 같다.
- 서비스의 `selector`와 파드의 `labels`가 일치하는가?
- 서비스의 `targetPort`가 파드의 컨테이너가 노출하는 `containerPort`와 일치하는가?
- 파드가 `Running` 및 `Ready` 상태인가?

## 6. 결론

쿠버네티스 서비스는 동적으로 변하는 파드들을 안정적으로 외부 또는 내부에 노출시키기 위한 핵심적인 네트워킹 오브젝트다. <b>레이블과 셀렉터</b>라는 간단하면서도 강력한 메커니즘을 통해 파드 집합을 정의하고, <b>kube-proxy</b>를 통해 실제 트래픽을 분산시키는 방식으로 동작한다.

이러한 서비스의 동작 원리를 이해하는 것은 쿠버네티스 기반의 마이크로서비스 아키텍처를 설계하고 문제를 해결하는 데 필수적이라고 할 수 있다. 결국 서비스는 파드 간의 의존성을 분리(decoupling)하여, 전체 시스템을 더 유연하고 확장 가능하게 만드는 중요한 역할을 담당하는 것이다.
