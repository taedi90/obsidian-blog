> [!SUMMARY]
> Docker는 메모리 한계 초과 시 컨테이너를 즉시 종료시키지만, Kubernetes는 자동 재시작과 Backoff 정책으로 대응하여 안정성을 높인다. 또한 Kubernetes는 `requests`와 `limits`라는 이중 구조를 통해 더 정교한 리소스 관리와 스케줄링을 제공한다는 점이 핵심적인 차이점이다.

## 💬 이슈

컨테이너 환경에서 리소스 제한(Resource Limit)을 설정하는 것은 시스템 안정성을 위해 필수적이다. 하지만 Docker와 Kubernetes는 리소스 한계를 초과했을 때 서로 다른 방식으로 대응한다. 쿠버네티스와 도커의 리소스 관리 방식이 다르다는 점은 알고 있었지만, 막상 운영 환경에서 이슈를 마주하면 매번 헷갈리는 부분이 있어 이번 기회에 다시 한번 정리해볼 필요성을 느꼈다.

특히 메모리 한계 초과 시 컨테이너(또는 파드)의 생명주기가 어떻게 관리되는지, 그리고 이것이 애플리케이션 안정성에 어떤 영향을 미치는지 명확히 이해하는 것이 중요하다고 판단했다.

## 🧗 해결

이 문제를 해결하기 위해 Docker와 Kubernetes의 리소스 관리 방식을 각각 살펴보고, 주요 차이점을 비교하여 정리했다.

### 1. Docker의 리소스 관리 방식

#### 1-1. 메모리 제한 초과: 즉시 종료

Docker는 컨테이너가 설정된 메모리 한계를 초과하면, 커널의 <b>OOM Killer(Out of Memory Killer)</b>를 통해 해당 컨테이너의 프로세스를 즉시 종료시킨다.

```bash
# 메모리 제한을 512MB로 설정한 컨테이너 실행
# 이 컨테이너 내부에서 512MB 이상의 메모리를 사용하면 즉시 종료된다.
docker run -m 512m --name test-container nginx
```

중요한 점은 Docker는 컨테이너를 단순히 중지시킬 뿐, 자동으로 재시작하지 않는다는 것이다. 컨테이너가 예기치 않게 종료되었을 때 다시 실행되게 하려면, `--restart` 정책을 명시적으로 설정해야만 한다.

#### 1-2. CPU 제한 초과: 성능 저하

CPU 리소스의 경우, 메모리와는 다르게 <b>스로틀링(Throttling)</b> 방식을 사용한다. 컨테이너가 설정된 CPU 한계에 도달하면, 컨테이너가 종료되는 대신 CPU 사용률이 강제로 제한된다.

```bash
# CPU 사용률을 0.5 코어로 제한하는 명령어
# 이 컨테이너는 CPU를 아무리 많이 사용해도 0.5 코어만큼의 성능만 낼 수 있다.
docker run --cpus="0.5" --name cpu-limited nginx
```

결과적으로 컨테이너가 종료되지는 않지만, 애플리케이션의 응답 속도가 느려지는 등 심각한 성능 저하를 경험할 수 있다.

### 2. Kubernetes의 리소스 관리 방식

#### 2-1. 메모리 제한 초과: 자동 재시작

Kubernetes도 메모리 한계가 초과되면 파드(Pod)를 종료시키지만, Docker와 가장 큰 차이점은 <b>자동 재시작(Automatic Restart)</b>이 기본적으로 동작한다는 것이다.

```yaml
# memory limit을 512Mi로 설정한 파드 예시
apiVersion: v1
kind: Pod
metadata:
  name: memory-limited-pod
spec:
  containers:
  - name: app
    image: nginx
    resources:
      limits:
        memory: "512Mi"
      requests:
        memory: "256Mi"
  restartPolicy: Always  # 기본값이 Always 이므로, OOMKilled 발생 시 재시작된다.
```

파드가 OOMKilled 되면, Kubernetes는 설정된 `restartPolicy`에 따라 자동으로 파드를 다시 시작한다. 이때 무한 재시작으로 인한 시스템 부하를 막기 위해, 재시작 간격을 점진적으로 늘리는 <b>백오프(Backoff) 정책</b>을 적용한다.

> [!IMPORTANT]
> Kubernetes의 자동 재시작 기능은 일시적인 메모리 급증을 처리하는 데 매우 유용하다. 하지만 근본적인 메모리 누수(Memory Leak) 문제가 있는 애플리케이션이라면, 파드가 끊임없이 재시작하는 `CrashLoopBackOff` 상태에 빠질 수 있으므로 주의해야 한다.

#### 2-2. Request와 Limit의 이중 구조

Kubernetes 리소스 관리의 또 다른 핵심은 `requests`와 `limits`라는 이중 구조를 제공한다는 점이다.

- <b>requests</b>: 파드 스케줄링 시 필요한 최소 보장 리소스. 노드는 이 `requests` 값의 합이 노드 용량을 초과하지 않는 선에서 파드를 할당받는다.
- <b>limits</b>: 컨테이너가 최대로 사용할 수 있는 리소스 한계. 이 값을 초과하면 앞서 설명한 정책에 따라 컨테이너가 종료되거나 성능이 제한된다.

이러한 구조 덕분에 Kubernetes는 단순히 리소스를 제한하는 것을 넘어, 더 정교한 스케줄링과 서비스 품질(QoS) 관리가 가능해진다.

#### 2-3. 노드 리소스 부족 시의 대응: 파드 축출

개별 파드의 리소스가 아닌 노드(Node) 전체의 리소스가 부족해지는 상황이 오면, Kubernetes는 <b>파드 축출(Pod Eviction)</b>을 통해 시스템을 보호한다. 이때 어떤 파드를 먼저 제거할지는 QoS 클래스(Class)에 따라 결정된다.

1.  <b>BestEffort</b>: `requests`와 `limits`가 모두 설정되지 않은 파드. 가장 먼저 축출 대상이 된다.
2.  <b>Burstable</b>: `requests`와 `limits`가 설정되었지만, 두 값이 다른 파드. BestEffort 다음으로 축출된다.
3.  <b>Guaranteed</b>: `requests`와 `limits`가 동일하게 설정된 파드. 가장 마지막까지 실행이 보장된다.

### 3. 주요 차이점 비교

| 구분 | Docker | Kubernetes |
| :--- | :--- | :--- |
| **메모리 초과 시** | 컨테이너 즉시 종료 | 파드 종료 후 자동 재시작 |
| **재시작 정책** | 수동 설정 필요 (`--restart`) | 기본 제공 (`restartPolicy`) |
| **리소스 계층** | 단일 레벨 (`limits`만 존재) | 이중 레벨 (`requests` + `limits`) |
| **관리 단위** | 개별 컨테이너 | 클러스터 전체 파드 |
| **축출 정책** | 없음 | QoS 기반 우선순위 축출 |

### 4. 운영 환경에서의 모범 사례

짧게나마 경험해본 바로는, 각 플랫폼의 특성에 맞춰 리소스를 설정하는 것이 중요하다고 느꼈다.

- **Docker 환경**: 애플리케이션의 메모리 사용 패턴을 미리 파악하고, 충분한 여유분을 두고 limit을 설정하는 것이 중요하다. 또한 `--restart=unless-stopped`와 같은 재시작 정책을 필수로 적용하여 예기치 않은 장애에 대비해야 한다.
- **Kubernetes 환경**: `requests`는 평상시 실제 사용량에 가깝게 설정하여 리소스 효율성을 높이고, `limits`는 순간적인 트래픽 증가(Burst)를 감당할 수 있도록 여유 있게 설정하는 것이 좋다고 판단했다.

> [!NOTE]
> 개인적으로 `requests`를 너무 낮게 설정하면 한 노드에 너무 많은 파드가 몰려 결국 전체 클러스터 성능이 불안정해지는 '노이지 네이버(Noisy Neighbor)' 현상을 겪을 수 있다. 반대로 너무 높게 잡으면 스케줄링 가능한 파드 수가 줄어들어 클러스터 리소스 활용률이 떨어지므로, 적절한 균형점을 찾는 것이 중요했다.

## ✅ 확인

실제 이 동작을 확인하기 위해 간단한 테스트를 진행해볼 수 있다.

- **Docker**: 메모리를 초과하는 프로세스를 실행하면 컨테이너가 `Exited` 상태로 바뀌는 것을 `docker ps -a` 명령으로 확인할 수 있다.
- **Kubernetes**: `kubectl get pods -w` 명령을 통해 OOMKilled된 파드가 `CrashLoopBackOff` 상태를 거쳐 재시작되는 과정을 실시간으로 관찰할 수 있다.
